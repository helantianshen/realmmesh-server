# 仓库四项优化与前后压力对照

日期：2026-10-24（Asia/Shanghai）。实施与隔离验证完成；本轮没有重新运行真实游戏客户端。

## 代码与保持不变的规则

- MaxOpen=10、连接寿命 30 分钟不变，MaxIdle 从 2 提高到 10。
- 堆叠 UPSERT 只返回实际库存 ID，保留完整物品数据比较及数量边界。
- Finish 条件 UPDATE RETURNING 只获取更新时间，去掉成功路径的最后一次完整操作查询；重复确认、竞争失败重读和退款逻辑保持不变。
- 存入持锁期间以单条 CTE 完成操作库存绑定和审计 INSERT，受影响行必须为 1；审计失败仍回滚库存和操作。

服务端 1 秒 RPC deadline、客户端流程 10 秒 deadline、测试 SQL 10 秒上限保持不变。同步提交、fsync、库存/操作/审计同事务和 UNKNOWN 处理不变；没有鉴权/策略缓存或异步审计。正常新存入 SQL 命令数 10→9，完整取出 19→18，计入 BEGIN/COMMIT。Prepare 与 Commit 没有缩减事务或检查。

## 对照方法

优化前业务源码在编辑前复制保存；两版使用相同 pgx 查询/建连探针、20ms 等待采样和正常同步文件日志。真实回环 TCP gRPC、已有 PostgreSQL 的随机隔离 schema。各版本三轮，每轮 7 场景 × 并发 8/32/64，每格调度 5 秒，含在途请求结束后的实际耗时计算吞吐。执行顺序为优化版、优化版、旧版、旧版、优化版、旧版。共 126 组；同一格的三轮观测是阶段交替对照，不是随机逐请求分配。

最初另有一轮旧版校验（before-1，21 组），期间有测试编译，因此保留其原始证据但不纳入对照，另跑 before-4 补足三轮。主对照期间不并行跑编译、数据库功能测试或磁盘压测。

吞吐 = 三轮成功逻辑流程总数 / 三轮实际耗时总和；完整取出一流程含 Prepare、Commit、Complete 三次 RPC。P50/P95/P99 表中值是三轮各窗口分位数的中位数，**不是合并所有请求重新计算的分位数**。原始 JSON 保留每轮值与范围；测量段延迟包含失败尝试，预热单独计数。

## WAL 存储复核

所有 126 组测试连接的 synchronous_commit 均为 on，观察查询错误数为 0。全局 fsync=on、full_page_writes=on、wal_sync_method=fdatasync。WAL 位于 PostgreSQL 数据卷内的真实目录，数据与 WAL 的设备号一致；宿主卷是 NVMe 上的 Btrfs，挂载含 compress=zstd:1。

使用只读 FS_IOC_GETFLAGS 核实目录及 64 个现存 WAL 段：目录 flags=0；64 个段均为 flags=1024，即 NOCOMPRESS=true、NOCOW=false。挂载默认压缩并不能说明这些 WAL 段正在压缩；尚未证明 CoW 是尾延迟的具体原因。没有修改任何属性或存储布局。

全部压力运行结束后，在同一 Docker 数据卷的 PGDATA 外创建独立临时文件，顺序进行 1000 次 8 KiB 随机数据写入加 fdatasync：P50=1.297ms、P95=1.642ms、P99=2.144ms、最大=6.958ms。该结果是独立文件的低争用测量，不是实际 WAL 压力下的延迟，不能排除高负载的存储尾部抖动。临时文件与容器内探针均已删除；没有改 PostgreSQL、宿主文件系统配置或迁移数据。

## 验证、结论与后续边界

- 已授权随机 schema 中的 `go test -race -count=1 ./...` 通过，`go vet ./...` 通过；无用例包不称为测试覆盖。仓储测试补充结果与审计字段、更新时间精度、重复确认原因保持、delivered 审计失败回滚。原有并发、碰撞、退款及幂等验证保留。
- 126 组、2346363 次测量尝试均完成库存净额、操作状态和逐操作审计结构核对。优化前 1024744 次尝试有 1 次超时，优化后 1321619 次尝试零错误；所有预热零错误。没有给超时操作自动退款或补发。
- 分散存取的低并发收益最明显；热点完整取出吞吐提升约 13%–17%。热点存入 c8/c32 的汇总吞吐反而下降约 10%/15%，不把本轮称为所有场景都改善；c64 的 P99 中位数也略升。SQL 和建连开销已减少，但 WAL 波动仍限制热点结果，尚需独立存储对照才能进一步归因。
- 下一步若继续处理热点尾延迟，应先对独立测试存储目标做相同同步持久化下的配对验证，再决定是否调整存储布局。本轮没有降低持久性或增大超时来换取结果。
