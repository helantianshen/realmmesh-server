# 仓库压力超时调查与优化方案

> 后续状态：前四项优化已实施并完成三轮前后压力对照，见 [优化对照报告](WAREHOUSE_OPTIMIZATION.md)。下文保留当时的历史测量和调查结论。

日期：2026-10-24（Asia/Shanghai）。状态：调查与对照试验完成，优化方案待审查，尚未修改业务代码或正式配置。

已确认的主要等待链是：**WAL 同步提交变慢 → 热点库存行锁迟迟不能释放 → 后续扣库/合并请求排队并占用数据库连接 → 更多请求等待连接 → 触及 1 秒 RPC deadline**。另有独立的连接复用问题：MaxOpen=10、MaxIdle=2 导致部分低并发分散负载频繁关闭和重建连接。两者贡献随场景变化，不能用一个“超时时间太短”解释全部结果。

## 调查方法与边界

复核原始日志后，在临时源码副本中添加测试探针，正式 Handler/Biz/Repo 和协议语义保持一致。使用已有 PostgreSQL 的随机 schema、真实回环 TCP gRPC；正常日志启用，客户端每笔流程 10 秒、每次 RPC 的正式 Kratos 默认 deadline 仍为 1 秒。

- pgx QueryTracer：连接取得之后的 SQL 执行/结果读取耗时，包括 BEGIN/COMMIT；只记录 SQL 类别、RPC 阶段、耗时和脱敏错误类型/SQLSTATE，不保存 SQL 参数。
- pgx ConnectTracer：真实物理连接次数和建连耗时；DBStats：连接排队、超出空闲上限的关闭次数。
- 每 20ms 查询 pg_stat_activity，只观察带本次诊断 application_name 的连接，统计行锁、WAL 等待、阻塞者数量和事务年龄。样本数是连接状态采样，不能直接当作精确毫秒。
- 对日志文件的同步 Write 单独计时；单个写调用可能包含多行，不将它冒称固定一条日志。
- 连接池对照按 Idle2 → Idle10 → Idle10 → Idle2 执行，MaxOpen 固定 10；每臂包含 5 场景 × 并发 8/64，每格调度 4 秒，合计 40 组。
- WAL 对照额外执行同步提交 off/on 各 4 组热点存取，每格 4 秒、MaxOpen/Idle 均为 10。off **仅设置在诊断连接的会话中**，用于切除前台持久化等待，未改变全局设置。它降低测试事务的持久性保证，不作为正式优化方案。

48 组完整对照共 195474 次逻辑操作，出现 8 次 DeadlineExceeded；库存、未知提交结果和逐操作审计结构均通过核对。另保留一次较早探索：热点取出重现 7 次超时，后一个窗口的串行预热也超时，未形成测量结果。后续夹具把预热失败单独记录并按操作 ID 对账，40+8 组完整对照没有预热失败。预热失败和探索结果没有混入正式对照统计。

临时探针、SQL/连接追踪和观察查询均有开销；与原始性能报告的绝对吞吐不作直接优化前后比较。4 秒短窗口与共享开发机也不足以给出长期容量。热点 8/64 并发是直接中心负载，绕过了 Mod 的同账户在途限制，不等同仅两个游戏服正常同时操作的数量。

## 1. 热点超时的直接等待点

原压力报告的 130 次超时，按服务端方法拆分为：

| RPC | 超时数 |
| --- | ---: |
| Deposit | 55 |
| CommitWithdrawal | 72 |
| PrepareWithdrawal | 1 |
| CompleteWithdrawal | 2 |

探索诊断在热点取出 8 并发窗口复现了下面的实际耗时：

| 观测项 | 结果 |
| --- | ---: |
| Commit 的库存条件 UPDATE | 最大 1000.35ms，P99 999.87ms |
| Commit 的 COMMIT | 最大 222.48ms |
| Complete 的 COMMIT | 最大 606.38ms |
| 后端事务年龄 | 最大约 1239ms |
| 单个等待者的阻塞后端数量 | 最大 6 |
| Go 连接池排队 | WaitCount=0 |
| 物理连接建立 | 30 次，最大 4.23ms，累计约 101ms |

该窗口采到 `Lock:transactionid`、`Lock:tuple`，并同时采到 COMMIT 的 `IO:WalSync` / `LWLock:WALWrite`。驱动在库存 UPDATE 以及 COMMIT 返回 deadline 错误，没有采到死锁 SQLSTATE。因此该窗口的主要直接原因是库存行等待叠加提交等待，建连耗时不能解释其近 1 秒的条件 UPDATE。

持锁范围来自正式代码：

- 存入的 UPSERT 获取库存行锁后，还要更新操作记录的 inventory_id、插入审计，直到提交后释放。
- 扣库的条件 UPDATE 获取库存行锁后，还要插入审计并提交。
- delivered 的 Complete 更新的是各自操作行，但其 WAL 持久化与其他事务共用写入/同步路径，仍可能影响正在持有库存锁的事务提交。

等待热点行的事务继续占用池连接。并发 64 时多个窗口累计连接池等待超过 200 秒，这是多个 goroutine 的等待总和，不能写成单次等待 200 秒。低并发没有池排队时仍能出现热点超时，说明单纯扩大 MaxOpen 不能解决这条链。

证据进一步限定了底层原因：当前同步方法为 fdatasync；PostgreSQL 数据卷位于 Btrfs，宿主挂载带 compress=zstd:1。**尚未验证数据库文件的实际 CoW/压缩标志，也未定位具体硬件/文件系统操作**。超时窗口前后 checkpoint 计数未变化，没有足够证据直接归因于 checkpoint、Btrfs CoW 或压缩中的某一项。

## 2. WAL 同步等待的对照证据

下面两臂使用相同正式业务路径、相同 MaxOpen/Idle=10 和相同 1 秒服务端超时。off 只是一项诊断干预。

| 场景 | 并发 | 同步 on 成功流程/秒 | 诊断 off 成功流程/秒 | on P99 / off P99，ms |
| --- | ---: | ---: | ---: | ---: |
| 热点存入 | 8 | 538 | 2086 | 80.3 / 13.4 |
| 热点存入 | 64 | 538 | 1984 | 250.6 / 70.7 |
| 热点完整取出 | 8 | 457 | 2197 | 50.1 / 5.6 |
| 热点完整取出 | 64 | 267 | 2577 | 408.5 / 43.7 |

off 时前台 WAL 等待样本为 0，COMMIT 的 P99 约 0.24–0.35ms；on 的相应 P99 约 2.13–7.97ms，另一次探索捕获了数百毫秒尾延迟。行锁等待仍然存在，但显著缩短。这支持同步提交等待是热点吞吐与尾延迟的重要因果因素。上述倍数是短窗口结果，不作为长期收益承诺，也不能据此把所有历史波动精确分摊到存储。

正式方案继续保留同步提交、fsync、库存与审计同事务。关闭同步提交会改变“中心返回成功后已可靠提交”的故障边界，不作为此次优化建议。

## 3. 连接池确有额外建连开销

`database/sql` 的 WaitCount 只覆盖达到 MaxOpen 后的排队，不统计尚未达到上限时直接创建连接的耗时。因此 WaitCount=0 不能排除建连问题。

两次 Idle2 与两次 Idle10 的 8 并发窗口：

| 场景 | Idle2 测量段新连接/4s | Idle10 新连接/4s | Idle2 流程/秒 | Idle10 流程/秒 |
| --- | ---: | ---: | ---: | ---: |
| 分散账户存入 | 1587–1593 | 0 | 969–1002 | 893–976 |
| 分散账户 16 KiB 存入 | 1460–1501 | 0 | 813–869 | 922–1560 |
| 分散账户完整取出 | 1767–1914 | 0 | 406–549 | 970–985 |

Idle2 的关闭数量与新连接数量近乎对应；分散取出每 4 秒花在建连上的累计时间约 7–8 秒。Idle10 测量段的 0 表示前面场景已经建立并保留了连接，不表示进程没有连接。

分散取出的 P99 从约 30–36ms 降到约 19ms，连接复用有明确收益；普通小载荷存入的吞吐并未同步提高，热点高并发在 Idle10 下也仍出现超时。**提高 MaxIdle 是减少已证实的开销，不是对所有瓶颈的修复。**

新对照中，Idle2 的分散小载荷存入 64 并发约 2463–2755 次/秒，16 KiB 约 1801–1863 次/秒。原报告“16 KiB 反而快很多”没有稳定重现，不能解释为大载荷算法更快。原测试缺少 SQL/WAL 采样，无法追溯断言每个旧窗口的确切原因；本轮证实了阶段性提交等待和连接复用是需要控制的变量。

## 4. 日志与 SQL 路径

同步日志 Write 在两臂中的 P99 约 0.006–0.013ms，最大约 1.03ms，量级不足以解释本次近 1 秒数据库等待。当前文件输出下，不优先引入异步日志系统；该结果不覆盖部署后的 journald、慢磁盘日志目标或远程日志。

正常新存入约 10 条 SQL 命令；一次完整取出约 19 条、2 个短写事务：Prepare 3 条、Commit 9 条、Complete 7 条，包含 BEGIN/COMMIT。新物理连接上的预编译还可能增加实际网络往返。这里存在可以独立审查的精简点，但尚未声称它们能解决存储尾延迟。

## 优化顺序与具体改动

### 第一批：连接复用与窄查询

1. **MaxOpen 保持 10，MaxIdle 从 2 调到 10。** 修改点为 `internal/data/postgres.go:42–44`，保留当前连接生命周期。减少反复建连与预编译，不通过增加数据库并行写入量掩盖热点行瓶颈。以相同负载验证连接数、关闭数、吞吐与 P99，不假定所有场景都会增速。
2. **存入 UPSERT 只返回库存 ID。** `internal/repo/warehouse.go:363` 当前 `RETURNING current.*` 回传完整 item_data，而调用方只使用 item.ID。改成窄字段返回可以减少持锁期间回传与扫描；SQL 的完整 item_data 等价条件必须保留，哈希碰撞拒绝规则不变。
3. **Complete 减少一次完整操作查询。** 当前先读操作、条件更新状态、写审计，最后又读完整操作。用条件 UPDATE RETURNING 获取需要的更新字段，去掉成功路径最后一次查询；若采用摘要读取，delivered 与退款分开处理，退款仍读取完整载荷及原库存身份。重复确认/退款竞争的读取分支继续保留。

这批不修改协议，不改鉴权或名单的实时生效约定，不延长超时。UPSERT/Complete 的改动目前是源码方案，尚未做原型或宣称性能收益。

### 第二批：缩短热点持锁区间

评估把“更新 operation.inventory_id + 插入资产事件”合成一条 SQL/CTE，减少存入拿到库存锁后的往返。必须继续先争取 operation_id，再变更库存；库存、操作、审计仍在同一事务。审计写入失败仍回滚，不移到异步任务，不在网络等待期间持有事务。

同一库存行的写入仍需串行协调；这批只缩短串行区间。完整取出跨越游戏服给予前后，不能为减少刷盘把两次写事务合并成等待游戏服回应的长事务。

### 并行处理：验证并改善 WAL 持久化路径

这是消除已捕获数百毫秒提交尾延迟所需的独立工作，连接复用和少一条 SQL 不能替代它：

- 在获授权的独立测试数据目录/存储目标比较同盘同步写延迟、不同同步方法及负载下的 COMMIT P99；保留同步提交和 fsync。
- 核实 PostgreSQL 数据/WAL 文件实际 CoW/压缩属性、磁盘争用与系统 I/O 尾延迟，再决定是否采用更适合数据库的存储布局或独立存储。Btrfs 是已观察到的环境事实，不能直接当成故障结论。
- 确有改善且验证通过后再安排配置或数据卷变更；本轮没有迁移目录、修改全局 PostgreSQL/文件系统配置或安装工具。

### 验证与过载边界

第一批先用相同连接上限、同步持久化和 1 秒 RPC 上限复测，再扩大到更长窗口、随机顺序、8/32/64 并发和至少三轮。分别报告每类 RPC、每个场景的错误率与未知结果数量，不能用大量幂等查询稀释写操作错误率。

保留并验证：重复 ID 参数绑定、唯一索引、完整数据碰撞比较、原子条件扣减、审计失败回滚、Complete 条件状态迁移、明确未发物一次退款。遇到超时已提交仍保留 UNKNOWN，不能通过“超时就退款/重试发物”消掉统计。

如仍有无法在截止时间内完成的过载，后续再设计有界准入和明确的错误语义。必须区分“本次请求没有开始”与“同 operation_id 的原操作未提交”；在此前没有证明原操作结果时，不能给客户端可退款的确定性拒绝。这不是本轮直接加队列或全局账户锁的依据。
